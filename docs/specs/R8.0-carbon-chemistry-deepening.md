# R8.0 — Deepening the carbon & chemistry layers

**Status:** spec written, not implemented · **Effort:** ~2–2.5 d serial, **~1 d wall-clock in parallel** (Wave A) + ~0.5 d Wave B + WP-F phase 1 (~0.5 d, optional)
**Origin:** post-R7.5 analysis of the chemical and carbon modules (2026-08-18). R7.5 fixed
what was *wrong*; this spec addresses what is *missing*.
**Depends on:** R7.5 (all of it — WP-B revises tests R7.5 froze, deliberately).
**Absorbs:** roadmap item R8.3 (carbon intervals) into WP-D/WP-E. R8.1/R8.2/R8.4 are untouched.
**Process:** dispatch per [`../DELEGATION_WORKFLOW.md`](../DELEGATION_WORKFLOW.md) (v2) — orchestrator
runs the baseline once, workspaces verified at spawn, foreground-only targeted tests, serial
integration. Wave A packages are mutually disjoint by file ownership and run concurrently.

## Framing — the asymmetry that shapes this spec

After R7.5 the two layers sit in opposite, clearly-labelled states:

- **The carbon layer is measured, tested, and frozen — but its boundary has honest holes.**
  The Tier-2 cement term is clinker-only (grinding/process electricity dropped — which is
  most of why advanced 0.836 < simple 0.912 kg/kg; that gap is *dropped scope wearing a
  fidelity costume*, currently enshrined by `test_tiers_same_boundary_simple_slightly_higher`).
  LC3's non-clinker half is zero-carbon in Tier 2 while calcined clay carries 0.25 kg/kg in
  this repo's own registry. The original CLAUDE.md brief asked for a **waste factor** that was
  never built. Exotic carbon and transport appear in the UI total but not the ticket breakdown.
- **The hydration layer is dimensionally sound and honest about being uncalibrated — and
  currently useless.** It computes heat, CH, and C-S-H that nothing consumes except a
  notebook printout. Its path forward is not more chemistry: it is (a) consumers for its
  outputs and (b) a calibration signal it can honestly claim.

Two standing rules inherited from R7.5, restated because Wave A agents must apply them:

1. **Never tune a coefficient to match a literature value.** Every new constant enters as a
   *declared, sourced* input (with the source in a comment), and every gate is a unit,
   conservation, bound, or band check — bands justified by the physics or by published EPD
   ranges, not reverse-engineered from the code's output.
2. **Changing a quoted number is allowed only deliberately.** WP-B exists precisely to change
   numbers; it must re-pin them with the justification in the commit message, R7.1-style.
   Every other package must leave existing numbers bit-identical at defaults.

## WP-A — Accounting boundary & ticket honesty

Three items, all at the metrics/ticket layer.

**A1 — Close the ticket reconciliation gap (the R7.5/WP-5 flagged leftover).** The UI's
displayed carbon (`compute_metrics`, `ui_logic.py:101`) includes `exotic_carbon(exotic)` and
(since WP-5) exotic transport mass; the downloaded mix ticket's breakdown includes neither,
so for a dosed mix the ticket's TOTAL ≠ the displayed number — on the artifact whose docstring
promises "the carbon breakdown sums exactly to the displayed carbon". Fix: `mix_ticket` and
`carbon_breakdown` gain `exotic=None`; the breakdown gains one `exotics` line
(Σ dose × factor) and passes `exotic` to `transport_carbon`; the call sites in `ui/compare.py`
/ `ui/inverse.py` / `src/cli.py` pass the dosing dict they already hold. Default `None` is
bit-identical to today.

**A2 — Waste factor (the un-built CLAUDE.md item).** Batched ≠ placed: 3–8% overbatch is
real carbon. One config control (`cfg_waste_factor`, slider 0–0.25, default 0.0, help text
explaining batched-vs-placed), persisted via `CONFIG_DEFAULTS` (it auto-joins the `ui_config`
session block — v4 schema already tolerates new keys, **no version bump**), plus
`"waste_factor": 0.0` in the CLI's `DEFAULT_RUN_CONFIG` (validated numeric in [0, 0.5)).
Application: metrics gain `carbon_as_placed = carbon × (1 + wf)` (and `cost_as_placed`
likewise); the ticket gains `config,waste_factor` and `carbon_kgCO2,TOTAL_as_placed` rows.
**The per-m³-batched numbers never change** — optimizers keep optimizing batched carbon (a
constant multiplier moves no optimum), and `wf=0` leaves even the new fields equal to the old.

**A3 — Carbon-intensity KPI.** `carbon_intensity = carbon / max(strength, 1)` (kg CO₂ per
m³·MPa, point-strength based — disclose that in the ticket row name, e.g.
`carbon_intensity_kg_per_m3MPa_point`). Added to `compute_metrics` output and the ticket. It
is the number procurement actually compares across bids. Do NOT add it as an optimizer
objective in this package (that changes Pareto fronts — Wave B decision at most).

**Gates:** ticket TOTAL == displayed carbon for a dosed mix (the A1 headline, asserted
end-to-end through a real `mix_ticket` string); all three features inert at defaults
(bit-identical metrics when `exotic=None`/`wf=0`); round-trip test covers `cfg_waste_factor`
(pure + AppTest levels, following `tests/test_session_roundtrip.py`'s established three-level
pattern); CLI rejects `waste_factor: -0.1` and `0.6` with a clean CliError; key-symmetry test
still passes without listing `ui_config` sub-keys manually.

**Traps:** the session export derives the `ui_config` block from `CONFIG_DEFAULTS` by
comprehension — add the key in ONE place (`ui/state.py`) and both export and import pick it
up; do not hand-edit `SESSION_FIELDS`. The ticket is consumed by `test_cli`'s golden
substring checks — extend, don't reorder existing rows.

## WP-B — Tier-2 cement-term scope completion

**This package deliberately changes quoted carbon numbers.** It is the only one allowed to.
Every changed pin is re-justified in the commit message with its derivation.

**B1 — Process electricity.** New constant in the carbon section:

```python
# Electricity for raw-meal prep, kiln drives, and cement grinding, per kg CEMENT
# (not clinker): ~100–120 kWh/t cement is typical for a modern dry-process plant
# (IEA/WBCSD GNR benchmark range); take 110 kWh/t = 0.11 kWh/kg as the declared default.
CEMENT_PROCESS_KWH_PER_KG = 0.11
```

`carbon_from_clinker` adds `cement_mass × CEMENT_PROCESS_KWH_PER_KG × grid_ef`, where
`grid_ef = GRID_EF[source["electricity"]]` when a clinker-source descriptor is present, else
`GRID_EF["grid_EU"]` as the documented legacy default. Placed **in `carbon_from_clinker`,
never in `clinker_scope_split`** (contract 2): the scope-split worked-example pins stay valid
because they are per kg *clinker* and this term is per kg *cement*.

Expected magnitude (derive, don't copy): legacy OPC cement term goes 0.836 → ≈0.864 kg/kg
(0.11 × 0.25 = 0.0275). The tier gap narrows ~36% and what remains is genuinely ICE-vs-model
methodology, not dropped scope.

**B2 — LC3 constituent recipe.** `data/oxide_compositions.json`'s LC3 record gains

```json
"constituents": {"calcined_clay": 0.30, "limestone_filler": 0.15}
```

(LC3-50 nominal proportions; the remaining 0.05 gypsum has no registry record and is
documented as excluded). `carbon_from_clinker` adds
`cement_mass × Σ frac × registry_factor(material)` using each constituent's A1–A3 factor from
`data/materials.json` (via the existing `get_material` import — read-only, WP-D owns that
file's *content* but these records' `carbon[0].value` fields are frozen values nobody
changes). OPC has no `constituents` key → term is 0 → OPC unaffected by B2.

**B3 — Bogue bare-dict hygiene.** `bogue_calculation({})` currently returns full OPC phases:
every missing oxide silently defaults to an OPC-typical value. Missing-oxide defaults should
not impersonate a real cement: require `CaO` and `SiO2` to be present (raise `ValueError`
naming the missing oxides), keep defaults only for the minor oxides (`Al2O3`, `Fe2O3`,
`SO3`), and preserve the registry-record path bit-identically (all registry records carry the
majors). Update the docstring's backward-compat note accordingly.

**Gates:**
- LC3 advanced cement term (legacy grid) lands in **[0.50, 0.65] kg CO₂/kg cement** — the
  published LC3 EPD band. This is the spec's one *external-validation* gate: the model
  finally reproduces a number the literature reports, without any coefficient having been
  fit to it (0.5 × 0.88 + 0.30 × 0.25 + 0.15 × 0.01 + 0.0275 ≈ 0.545 — show the derivation
  in the test comment).
- Tier ordering preserved: simple > advanced for high-clinker OPC still holds
  (0.912 > ≈0.864/kg); `test_tiers_same_boundary_simple_slightly_higher`'s tolerance is
  re-derived, not loosened blindly — the commit message shows the new expected gap.
- `clinker_scope_split` and every pin in `test_clinker_source.py`'s worked-example table
  pass **byte-unmodified** except any that assert `carbon_from_clinker` totals (re-pin those
  with derivations).
- With a clinker-source descriptor, the process term uses the *descriptor's* grid: assert
  hydro vs grid_CN differ by exactly `0.11 × (0.55 − 0.004) × cement_mass`.
- `bogue_calculation({"CaO": 65})` raises naming `SiO2`; registry-path phases bit-identical.
- Do NOT regenerate `docs/BENCHMARKS.md` or touch `docs/PAPER.md` — quoted-number sweeps are
  Wave B (the orchestrator checks whether any quoted carbon actually moved).

**Traps:** `test_cli.py::test_predict_matches_compute_metrics` compares CLI to a live
`compute_metrics` call — both move together, no edit needed there (and that file is WP-A's,
not yours). The advanced tier is only exercised with `advanced=True` configs; make sure at
least one gate runs the *default* legacy path so the grid_EU fallback is covered.

## WP-C — Hydration-layer consumers (`src/thermal.py`, additive only)

A new module that finally gives the uncalibrated-but-dimensionally-sound hydration layer a
job. **Zero edits to existing files** — pure functions consuming `analyze_mix` /
`hydration_kinetics` output, wired into the UI/ticket by Wave B, not here. Every docstring
carries the UNCALIBRATED inheritance notice: these outputs are order-of-magnitude planning
signals derived from a dimensionally-checked, unfitted model — bounds and flags, not
predictions.

**C1 — Adiabatic temperature rise + mass-pour flag.**
`adiabatic_temperature_rise(mix, cement_type="OPC") -> float`: full-hydration heat
(`hydration_kinetics` at large age, α → α_ult) × cement mass / (ρ·c_p), with
`CONCRETE_DENSITY = 2400 kg/m³` and `SPECIFIC_HEAT = 1.0 kJ/(kg·K)` as declared constants.
A 350 kg/m³ OPC mix at ≈300 kJ/kg gives ΔT ≈ 44 °C — sanity band, not calibration.
`mass_pour_flag(delta_t, threshold=20.0) -> Optional[str]`: advisory string above the
threshold (ACI 207's ~19–20 °C differential guidance; cite in comment), styled after
`physical.workability_flag`.

**C2 — Maturity-based curing estimate.** `equivalent_age(t_days, temp_c, ref_c=20.0,
activation_kj_mol=41.6) -> float` (Arrhenius per ASTM C1074; Ea default mid-range 40–45,
declared) and `curing_days_at_temperature(mix, target_alpha_fraction=0.7, temp_c=20.0)`:
invert the hydration model's α(t) for the age reaching `target_alpha_fraction × α_ult`, then
rescale via equivalent age. This is the physically-grounded successor to
`estimate_curing_time` — but the old heuristic is NOT edited or rewired here (contract 3);
Wave B decides the switchover with its own displayed-numbers review.

**C3 — Carbonation-uptake upper bound.** `carbonation_co2_bound_kg_m3(analysis) -> float`:
`CH_remaining_kg_m3 × 44.01/74.09` (molar CO₂/Ca(OH)₂). Docstring states precisely what it
is: an **upper bound on portlandite re-carbonation**, excluding C-S-H carbonation, outside
the A1–A4 boundary, informational only (EN 16757 Annex BB is the reporting frame). An
uncalibrated model can still bound honestly; it cannot predict.

**Gates:** ΔT for the reference mix in a broad physics band (30–60 °C) asserted as a *unit*
check with the derivation in the comment; `equivalent_age` = t at ref temperature exactly,
monotonic in temperature, ~2.2–2.6× at 35 °C vs 20 °C (Arrhenius arithmetic, shown);
carbonation bound scales linearly with CH and is 0 when slag+ash consume the pool; every
function total-safe on an `analyze_mix` result whose `hydration is None` (LC3) — degrade to
None/0 with a reason, never raise; no import from `ui/` or `models.py`.

## WP-D — Registry conventions, compliance & uncertainty data

Registry fields + views + pure helpers. Nothing user-visible until Wave B. Existing record
*values* untouched; existing pinned views pass unmodified (contract 4).

**D1 — Allocation basis.** Every carbon record gains `"allocation"`: `"byproduct-mass"` for
slag/ash/silica_fume/rice_husk_ash (their low factors *assume* it — an EN 15804 tender
challenge turns on exactly this), `"process"` for cement/calcined_clay/metakaolin,
`"none"` for the rest. `validate_material` requires the field on every carbon record with a
value from `ALLOCATION_BASES`; `carbon_provenance` is NOT changed here (Wave B may extend
disclosure).

**D2 — Restrictions hook (chloride first).** `calcium_chloride` gains
`"restrictions": {"reinforced_concrete": "prohibited-or-limited",
"reference": "ACI 318 ch. 19 chloride limits / EN 206"}`. New in `src/exotics.py`:
`compliance_warnings(exotic: dict) -> list[str]` returning one advisory string per dosed
material with a restriction (shape mirrors `workability_flag`). This is the data hook R8.2's
compliance layer will consume; the UI wiring is Wave B.

**D3 — Uncertainty propagation helper.** `factor_uncertainties_view() -> dict[str, float]`
(the registry's existing per-record `uncertainty` fields, finally read) and
`carbon_interval(mix, factors, uncertainties, exotic=None) -> tuple[float, float]` in
`src/materials.py`: independent-error linear propagation,
`σ² = Σ (mass·factor·rel_unc)²`, interval = total ± 1.96σ. Docstring honestly lists what it
ignores (correlation between factors, transport, the clinker model — Monte Carlo for the
clinker path is future work, noted for Wave B/R8). Pure math on plain dicts — no import
cycles.

**D4 — Per-material transport data.** `TRANSPORT_MODE_EF = {"truck": 0.1, "rail": 0.03,
"ship": 0.015}` (kg CO₂/t·km, declared defaults with sources), optional per-record
`"transport": {"mode": "truck", "km": 50}` blocks — populate: aggregates 30 km truck,
cement 200 km truck, slag/ash 150 km truck, exotics 500 km truck except
graphene_oxide/nano_silica 10000 km ship — and `material_transport_carbon(mix, exotic=None,
overrides=None) -> float` summing per-material `mass × km × mode_ef / 1000`, falling back to
nothing (0-contribution) for materials without a block. **`chemistry_simple.transport_carbon`
is not touched** — Wave B decides how the per-material path and the global-km path coexist
(fallback vs replacement) with the number-change review that decision deserves.

**Gates:** all existing `EXPECTED_*` pins pass unmodified (the acceptance proof that new
keys are invisible to old views); `validate_material` rejects a missing/unknown allocation
with a readable message; `compliance_warnings({"calcium_chloride": 5})` returns exactly one
warning naming the reference and `{}`/undosed returns `[]`; `carbon_interval` with all-zero
uncertainties collapses to (total, total), and an EPD-style tightened uncertainty narrows the
interval monotonically; a registry-edit test (established `set_materials_path`/`finally`
pattern) shows a transport-block edit flowing into `material_transport_carbon` with no code
change.

**Trap:** `test_new_material_via_registry_json` constructs a record in-line — it will now
fail validation without an `allocation` field; extending THAT test's record is a legitimate
edit (WP-D owns the file), but the bit-identical view pins are not.

## WP-F — Powers-calibrated hybrid, **phase 1 only** (independent; delegable)

The big bet, deliberately fenced. The full idea — physics-as-baseline + GBM-on-residuals —
is R9-class and **not delegable as written**. Phase 1 *is* delegable because it is a fitting
script with statistical gates and zero runtime integration:

- `scripts/fit_powers.py`: for each UCI row, compute α(t) from the hydration model (OPC
  assumption documented), gel-space ratio `X = 0.68α / (0.32α + w/c)` (Powers' constants,
  declared), fit `f = A·X^n` (A, n free; n expected ≈ 2.6–3, Powers' canonical 3) by least
  squares on the 1030 measured strengths; emit `models/powers_calibration.json` (fitted A, n,
  fit R², residual std, per-age-bucket residual means) and a markdown report section printed
  to stdout.
- **Honesty constraints:** the hydration model's *kinetic* constants are NOT refit — only
  Powers' (A, n) at the interface, so the uncalibrated layer stays labelled uncalibrated and
  the fit claims exactly one thing: "α(t) as currently modelled, pushed through Powers,
  correlates with measured strength this well." Report R² whatever it is; an R² of 0.5 is a
  *finding*, not a failure — do not tune the hydration layer to raise it.
- **Gates:** deterministic under fixed seed; JSON artifact schema-tested;
  fitted n in a broad sanity band [1.5, 4.5] *reported* (asserted only as "finite and
  positive" — the band is information, not a pass bar); no import from `ui/`; runtime code
  paths (`models.py`, predictors) untouched — integration is a *future spec* that will cite
  this artifact's numbers.

## Accepted risks / explicitly out of scope

- `calculate_mix_cost`/`calculate_embodied_carbon` factors-dict iteration footgun: still
  documented-only (R7.5's accepted risk stands).
- Biogenic/waste kiln-fuel accounting conventions: still comment-level disclosure; a
  convention field rides with R8.2's jurisdiction packs, where it has a consumer.
- C-S-H carbonation, Monte-Carlo clinker uncertainty, cost-side uncertainty: named in
  docstrings as exclusions, not attempted.
- `age`-aware carbon (curing energy): out entirely — no data, no boundary agreement.

## Sequencing & scope

- Wave A: WP-A ∥ WP-B ∥ WP-C ∥ WP-D ∥ WP-F — five agents, disjoint files, one shared rule:
  each lands code + tests in one commit, targeted foreground tests only, baseline handed in
  the prompt, no push.
- Wave B: WP-E after Wave A integrates serially (orchestrator gates each package with its
  targeted tests + the unowned must-stay-green files, one full suite at the end).
- Do **not** weaken a gate to make it pass; the WP-B number-change protocol is the only
  sanctioned way a quoted value moves. If a gate cannot be met honestly, report the number
  and why — the R7.1/R7.5 convention, unchanged.
