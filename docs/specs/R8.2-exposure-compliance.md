# R8.2 — Exposure-class compliance layer

**Status:** spec written, not implemented · **Effort:** ~1 d serial, **~0.5 d wall-clock in parallel** (Wave A) + ~0.4 d Wave B
**Depends on:** R8.0 (WP-D's `restrictions` hook and `compliance_warnings` are the seed this generalises; WP-A's ticket rows are the disclosure surface). R7.1's conformal lower bound is load-bearing — see §Design.
**Process:** dispatched per [`../DELEGATION_WORKFLOW.md`](../DELEGATION_WORKFLOW.md) v2.

## Motivation

Real specifications are not written in bare 28-day strength. They are written in **exposure
classes** — XC4, XD2, XS3, F2, C1 — each carrying deemed-to-satisfy limits on water/binder
ratio, minimum cement content, minimum strength class, air entrainment, and SCM proportions.
An engineer cannot defend a mix to a checker, and a buyer cannot put it in a tender, until it
reports against those classes. This is the step where the tool stops being a strength
calculator and starts being a specification instrument (`../BUSINESS_REPORT.md` §6).

It also makes the **national-variation cost visible**: the same mix, checked across
jurisdictions in one table, shows exactly where a design that passes in one regime fails in
another — the fragmentation the business report argues is the sector's real friction.

## The honesty problem this spec must solve

**The deemed-to-satisfy values are safety-relevant numbers from paywalled standards.** A model
transcribing EN 206 Table F.1 or BS 8500-1 Table A.4 from memory will produce plausible,
authoritative-looking limits that may be wrong — and an engineer could rely on them. This is
the same class of risk as the uncalibrated hydration layer, and it gets the same treatment,
one level stronger:

1. **Every pack carries `source.verified: false` and a `verification_note`** until a human has
   checked it against the actual standard. The schema *requires* the field; a pack cannot omit
   it.
2. **The engine never emits a bare boolean.** Results are `PASS` / `FAIL` / `UNKNOWN` per rule,
   and the top-level verdict of an unverified pack is always qualified.
3. **Every user-facing surface says advisory.** The ticket row, the UI panel, and the CLI
   output all state that this is a design-exploration check against unverified reference data,
   not a compliance certification, and name the standard the user must check against.
4. **`UNKNOWN` is a first-class result, not a failure.** A rule the mix cannot be evaluated
   against (no air-content model, k-value substitution not modelled) reports `UNKNOWN` with a
   reason. Silently passing an unevaluated rule would be the dangerous failure here.

If an implementer cannot source a value confidently, the correct action is to **omit the rule**
(the engine reports `UNKNOWN: rule not present in pack`) — never to guess a plausible number.
An incomplete pack is honest; a fabricated one is a liability.

## Design

### The pack schema (the Wave A contract — inlined in full, not referenced)

One JSON file per jurisdiction in `data/exposure_packs/`. This schema is **frozen for Wave A**:
WP-1 codes against it, WP-2 authors against it, and neither may change it unilaterally.

```json
{
  "pack_id": "en206",
  "name": "EN 206:2013+A2:2021 — generic European recommended values",
  "jurisdiction": "EU (generic; national annexes override these values)",
  "source": {
    "standard": "EN 206:2013+A2:2021",
    "table": "Table F.1 (recommended limiting values for composition)",
    "verified": false,
    "verification_note": "Indicative values for design exploration. NOT verified against the published standard; national annexes vary. Check against the standard before any structural use."
  },
  "strength_basis": "conformal_lower_bound",
  "classes": {
    "XC4": {
      "description": "Corrosion induced by carbonation — cyclic wet and dry",
      "max_w_b": 0.50,
      "min_cement_kg_m3": 300,
      "min_strength_MPa": 30,
      "min_air_pct": null,
      "max_scm_fraction": {"ash": 0.33, "slag": 0.80},
      "notes": "w/b uses total binder; k-value substitution not modelled here."
    }
  }
}
```

Field rules: `max_w_b`, `min_cement_kg_m3`, `min_strength_MPa`, `min_air_pct` are a number or
`null` (`null` ⇒ the rule does not apply to this class, distinct from absent ⇒ `UNKNOWN`).
`max_scm_fraction` is a mapping of mix key → max fraction *of total binder*, or `null`.
`strength_basis` is `"conformal_lower_bound"` or `"point"` (see below).

### Strength is checked against the conformal LOWER BOUND

You do not certify a mix on a mean prediction. R7.1 made point estimate and interval come from
one distribution; R7.5 kept them coherent. Compliance therefore compares
`min_strength_MPa` against `predictor.predict_interval(...)` **lower** bound by default
(`strength_basis: "conformal_lower_bound"`), and the result discloses which basis it used. This
is the same principle as robust mode, applied to specification rather than optimisation — and
it is the single most defensible design decision in this spec.

### Result shape

`check_compliance(mix, pack, *, strength=None, strength_lo=None, air_pct=None) -> dict`:

```python
{"pack_id": "en206", "class": "XC4", "verdict": "PASS" | "FAIL" | "UNKNOWN",
 "advisory": True,                      # always True while source.verified is False
 "rules": [{"rule": "max_w_b", "required": 0.50, "actual": 0.47,
            "result": "PASS", "basis": None, "reason": None}, ...],
 "unknown_count": 1, "source": {...}}
```

Verdict aggregation: any `FAIL` ⇒ `FAIL`; else any `UNKNOWN` ⇒ `UNKNOWN`; else `PASS`. An
`UNKNOWN` never upgrades to `PASS`.

### WP-1 — Compliance engine

`src/compliance.py`, pure functions, no Streamlit, no model imports (the caller supplies
strength values — keeps the module testable and free of circular imports):

- `load_packs(path=None) -> dict[str, dict]` — reads `data/exposure_packs/*.json`, cached per
  path, `set_packs_path()` override mirroring `materials.set_materials_path` exactly (the
  established pluggability pattern: a jurisdiction is a JSON drop-in, not a code change).
- `validate_pack(pack) -> str | None` — schema validation in `materials.validate_material`'s
  shape. **Must reject** a pack missing `source.verified`, a class with an unknown field, a
  non-numeric limit, or `max_scm_fraction` values outside [0, 1].
- `mix_w_b(mix) -> float` and `mix_binder(mix) -> float` — total binder = cement + slag + ash
  (consistent with `chemistry_simple.estimate_curing_time` since R7.5; do not re-derive).
- `check_compliance(...)` — per the result shape above.
- `compare_jurisdictions(mix, class_map, **kw) -> list[dict]` — the same mix across packs,
  one row per (pack, class); this is what makes national variation visible.

Ship `data/exposure_packs/_fixture.json` — a small, obviously-synthetic pack (`pack_id:
"_fixture"`, `name` saying "synthetic test fixture, not a real standard") so the engine's tests
never depend on WP-2's real packs landing. `load_packs` must **exclude** `_`-prefixed packs from
its default listing so a fixture can never appear in the UI.

**Gates:** `UNKNOWN` when a rule is absent, `PASS`/`FAIL` correctly at boundaries (exactly at
the limit is PASS — deemed-to-satisfy limits are inclusive); an `UNKNOWN` rule never yields a
`PASS` verdict; `advisory` is `True` whenever `source.verified` is false; strength checked
against `strength_lo` when supplied and the result's `basis` says so; `validate_pack` rejects
each malformed case with a readable message; a pack dropped into a temp dir surfaces through
`set_packs_path` with no code change (the `materials`-style registry-edit test).

### WP-2 — Jurisdiction packs

Three packs against the frozen schema: **EN 206** (generic European, XC/XD/XS/XF/XA classes),
**BS 8500-1** (UK national annex — the same classes with UK-specific limits, which is the point:
it *differs* from generic EN 206), **ACI 318-19** (US: exposure categories F, S, W, C — a
genuinely different taxonomy, not a relabelled EN set).

**The sourcing rule is the deliverable's quality bar.** Every pack sets
`source.verified: false` with a verification note naming the standard and table. Where a value
cannot be sourced confidently, **omit the rule entirely** so the engine reports `UNKNOWN` —
do not guess. It is better to ship EN 206 with four confident rules per class than eight
half-remembered ones. Record in the pack's `notes` what was omitted and why.

`tests/test_exposure_packs.py`: every shipped pack passes `validate_pack`; every pack carries
`verified: false` (a `true` would need human sign-off and a test change — that friction is
deliberate); ACI's taxonomy is genuinely distinct (assert its class ids are not the EN set);
BS 8500 and EN 206 differ on at least one shared class's limits (assert the difference exists —
if they are identical, one of them was copied rather than sourced); no pack contains a class
whose every rule is absent.

### WP-3 — Wave B integration (serialised, after Wave A merges)

1. `compute_metrics` gains an optional `compliance` block (selected pack + class from config),
   passing the conformal lower bound as `strength_lo`.
2. Compare tab: a compliance panel per mix — verdict, per-rule table, and the advisory banner.
   The cross-jurisdiction table (`compare_jurisdictions`) is the feature's headline.
3. Ticket rows: `compliance,<pack>.<class>,<verdict>`, one row per failing/unknown rule with
   its required-vs-actual, and a mandatory `compliance,advisory,"..."` disclosure row.
4. CLI: `--exposure <pack>:<class>` on `predict`; validated at the boundary in
   `validate_clinker_source`'s style (unknown pack/class ⇒ clean `CliError` naming valid ids).
5. **Optimizer constraints:** `generative_ga` / `nsga` accept an optional compliance
   constraint; infeasible candidates are penalised in the scalarised objective and constrained
   in NSGA (mirroring the existing in-support/volume constraint machinery — do not invent a
   new mechanism). Gate: a constrained run returns designs that pass the requested class, or
   reports honestly that none were found in the envelope.
6. Config: pack/class selectors from `load_packs` (never hardcoded lists), added to
   `CONFIG_DEFAULTS` in `ui/state.py` only.

**Wave B gates:** defaults inert (no pack selected ⇒ every existing number bit-identical); the
advisory row is present on every ticket that carries a verdict; a mix at exactly a limit passes;
the cross-jurisdiction table shows at least one mix passing in one jurisdiction and failing in
another (the national-variation demonstration, asserted).

## Accepted exclusions (documented, not attempted)

- **k-value / SCM-efficiency substitution** (EN 206 §5.2.5): w/b uses total binder with no
  efficiency factor. Named in every pack's `notes` and in the engine docstring.
- **Air content**: no model predicts it; `min_air_pct` rules report `UNKNOWN` unless the caller
  supplies a measured `air_pct`. Do not invent an air model to make a rule evaluable.
- **Cover, curing regime, chloride content by test**: out of scope — these are not mix-design
  properties the tool computes.
- **National annexes beyond BS 8500**: the pack mechanism makes them a data contribution.

## Sequencing

WP-1 ∥ WP-2 (disjoint; the schema above is the contract), then WP-3 serialised after both
merge. Each package: code + tests in one commit, targeted foreground tests only, baseline from
the orchestrator, no push. **Do not weaken a gate to make it pass**, and do not fabricate a
limit value to fill a pack — the `UNKNOWN` path exists precisely so honesty has somewhere to go.
