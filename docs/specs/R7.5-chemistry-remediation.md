# R7.5 — Chemistry layer remediation

**Status:** spec written, not implemented · **Effort:** ~1.25 d serial, **~0.7 d wall-clock in parallel**
**Origin:** adversarial review of the base chemistry models (2026-08-15), not a planned roadmap item.
**Depends on:** nothing. R7.1–R7.4 shipped; this touches none of their surfaces.

## Why this is R7.5 and not R8

R8's slot is spoken for (the specification-tool theme). These are defects in the
*existing* chemistry layer, found by review, and they belong to R7's theme —
"trustworthy to the edge" — so they reopen it for one bounded remediation wave rather
than displacing H2. R7.1–R7.4 stay closed and shipped; this gets its own effort-log row.

## The finding that frames the whole spec

The review split cleanly in two:

- **The carbon accounting is sound.** Calcination stoichiometry (0.53 kg CO₂/kg clinker
  vs. 0.510 computed from the shipped 65% CaO, plus MgCO₃ — matches the WBCSD/CSI
  default), the kiln electricity derivation (3.4 GJ/t ÷ 3.6 = 0.944 ≈ 0.95 kWh/kg), the
  Scope 1/2 split, and the capture-energy-survives-capture logic all survive attack.
  The Tier-1/Tier-2 boundary equality is real and tested. **Do not touch any of it.**
- **The hydration/Bogue layer is not sound.** A factor-of-10 unit error, a dimensionally
  incoherent pozzolanic reaction, and a double-spent portlandite budget. It is
  unreferenced by the app and CLI but *is* called by `notebooks/experiment_ga.ipynb`,
  which CLAUDE.md treats as a primary deliverable — so it is user-facing and entirely
  untested (`tests/test_chemistry.py` covers only the carbon tiers).

**The judgment that must survive implementation:** we can fix *dimensional* correctness,
because that is verifiable against physics. We **cannot validate the hydration model** —
this repo contains no calorimetry, no degree-of-hydration data, and no CH measurements.
So the gates below are unit-correctness and conservation gates, never "matches the
literature value." An implementer who tunes coefficients until a number looks right has
made the layer *more* dangerous, not less: it would then carry the appearance of
calibration with none of the substance. Fix the units, enforce the conservation laws,
label the layer honestly, and stop.

## Parallelisation model

Six of the nine defects live in `src/chemistry_advanced.py`, so partitioning by *finding*
would serialise everything. The partition below is by **exclusive file ownership**, which
is the only property that makes concurrent edits safe.

**Rule: exactly one work package may write each file.** A package may freely *read*
(import from) files it does not own, subject to the frozen-surface invariants below.

| WP | Exclusive write ownership | Findings | Est. |
|---|---|---|---|
| **WP-1** Hydration/Bogue layer | `src/chemistry_advanced.py`, `data/oxide_compositions.json`, `tests/test_hydration.py` *(new)*, `notebooks/experiment_ga.ipynb` | 1, 2, 3, 6, 7, 8 | ~0.5 d |
| **WP-2** Exotic volume accounting | `data/materials.json`, `src/materials.py`, `src/physical.py`, `src/exotics.py`, `tests/test_materials.py`, `tests/test_physical.py`, `tests/test_exotics.py` | 4 | ~0.25 d |
| **WP-3** Curing-time heuristic | `src/chemistry_simple.py`, `tests/test_chemistry.py` | 9b | ~0.15 d |
| **WP-4** Clinker-source validation | `src/cli.py`, `tests/test_cli.py` | 5 | ~0.15 d |

WP-1 through WP-4 have **no file overlap** and may run fully concurrently, in any order,
by four separate agents.

**Wave B — WP-5 (transport mass), runs only after WP-1 and WP-3 have merged.** It is
serialised because the transport heuristic is triplicated across `chemistry_simple.py`
(WP-3's file), `chemistry_advanced.py` (WP-1's file), and `ui_logic.py`, and all three
must change atomically or the tier-equality test breaks. Do not attempt it in Wave A.

### Frozen surfaces (the invariants that keep Wave A safe)

These are not style preferences; violating one breaks another agent's tests.

1. **WP-1 must not change the behaviour of `embodied_carbon_advanced`,
   `carbon_from_clinker`, `clinker_scope_split`, `clinker_factor_for`, or the
   `CALCINATION_EF` / `FUEL_EF` / `GRID_EF` / `KILN_KWH_PER_KG` tables.** WP-1 owns the
   file they live in, which makes this an ownership hazard rather than a merge conflict.
   `tests/test_chemistry.py` (WP-3's) and `tests/test_clinker_source.py` (unowned, must
   stay green) both exercise these. WP-1's scope is strictly the Bogue → hydration →
   pozzolanic → `analyze_mix` chain.
2. **WP-1 must not rename or remove `FUEL_EF` / `GRID_EF`.** WP-4 imports both.
3. **WP-2 must keep `densities_view()` core-only.** `tests/test_materials.py` pins
   `EXPECTED_DENSITIES` to exactly seven entries as an R6.1 bit-identical migration gate.
   Add exotic densities through a *separate* view (see WP-2 design) rather than widening
   the pinned one.
4. **WP-2 must not wire exotic volume into `ui_logic.py` or `ui/`.** It delivers the
   capability and its tests; surfacing it is deliberately out of scope (see WP-2 §Non-goals).
5. **Nobody touches `src/models.py`, `src/generative_ga.py`, `src/nsga.py`, `src/aco.py`,
   `src/bayesian.py`, `src/amortized.py`, or `ui/`.** No finding requires them.

### Shared conventions

Match the repo's existing test idiom, which every reviewer here already expects: pinned
`EXPECTED_*` constants for migration gates, `set_materials_path(...)` with a `finally`
reset for registry overrides, `pytest.importorskip` for optional stacks, and a module
docstring naming the spec item the file gates. Each WP lands its own tests in the same
commit as its code. Run `ruff check .` and the full suite before declaring done.

## WP-1 — Hydration / Bogue layer

### Current state (measured, not asserted)

Run against the shipped OPC oxides (`CaO 65.0, SiO₂ 21.0, Al₂O₃ 5.5, Fe₂O₃ 3.0, SO₃ 2.5`):

```
Bogue OPC: C3S=56.6 C2S=17.5 C3A=9.5 C4AF=9.1  sum=92.7%     <- correct, plausible
heat code=31.9 kJ/kg | dimensionally correct=319.4 kJ/kg      <- 10x low
CH pool (wt%) = 12.7 ; slag draws 12.7 + ash draws 9.7 = 22.4 <- OVERSPENT
```

The Bogue coefficients themselves are the textbook values, correctly transcribed, and
C2S correctly uses the *unclamped* C3S. That part is right — leave it alone.

### Design

**1. Heat units (`hydration_kinetics`).** The phases are wt% (C3S ≈ 56.6), so converting
to per-gram-of-cement needs ÷100 for percent→fraction. Since 1 J/g is exactly 1 kJ/kg, no
further conversion applies. The code's `/ 1000.0` carries an extra factor of 10.
Change to `/ 100.0`.

**2. One unit system (`pozzolanic_reaction`, `HydrationState`).** Today
`min(CH_available, pozzolan_mass * 0.2 * extent)` compares wt%-of-clinker against kg/m³.
Convert the whole chain to **kg/m³**, which is the unit `analyze_mix` already receives and
the only one in which "total C-S-H" means anything per batch. The conversion from Bogue's
wt%-of-clinker to kg/m³ is `phase_pct / 100 × cement_mass × clinker_factor`.

Rename every field on `HydrationState` and the reaction's returns to carry its unit
(`CSH_kg_m3`, `CH_kg_m3`, `heat_kJ_per_kg_cement`). This is a deliberate breaking change:
it is the only way a future reader cannot repeat the mistake, and WP-1 owns the sole
caller (the notebook).

**3. Conserve the portlandite budget (`analyze_mix`).** Thread a running pool through the
sequential reactions instead of passing the same `CH_content` to each:

```
ch_remaining = hydration.CH_kg_m3
for pozzolan in (slag, ash):        # order documented as a model limitation
    consumed, csh = pozzolanic_reaction(ch_remaining, ...)
    ch_remaining -= consumed
```

Document that the result is order-dependent — that is a real property of the sequential
approximation, and stating it is better than hiding it behind an arbitrary split.

**4. Honour `cement_type` (`analyze_mix`).** It currently hardcodes
`oxide_compositions["OPC"]` and calls `carbon_from_clinker(cement)` with no cement type,
so an LC3 mix silently reports OPC phases and OPC carbon. Add `cement_type` and
`clinker_source` parameters and thread them through.

**5. Refuse Bogue on blended cements.** Bogue applies to Portland *clinker* oxides only,
but `data/oxide_compositions.json` now carries an LC3 entry with a full oxide set that
`bogue_calculation` would consume without complaint (masked today only by defect 4). Add
an explicit `"bogue_valid": true|false` flag to each record in that JSON — `true` for OPC,
`false` for SLAG / FLY_ASH_* / LC3 — and have `bogue_calculation` raise `ValueError` when
applied to a record flagged `false`. `analyze_mix` reports phases as unavailable for a
blended cement rather than fabricating them.

**6. Stop treating slag as a pozzolan.** The registry already classifies slag as
`"reactivity_class": "latent-hydraulic"` and fly ash as `"pozzolanic"` — read those
values from `data/materials.json` (read-only; WP-2 owns that file but is not changing
these keys). Give latent-hydraulic materials a distinct path: they principally
self-hydrate with CH as an activator rather than consuming it stoichiometrically, so
their CH draw per kg is much lower than a true pozzolan's. Keep the coefficients as
**declared placeholders** — do not invent precision.

**7. Label the layer.** Module docstring, `analyze_mix` docstring, and the notebook output
all state that this layer is dimensionally checked but **uncalibrated** — no calorimetry
or DoH data backs it. Contrast with the carbon layer, which is measured and tested.

### Acceptance gates

- At α = 1 with the shipped OPC oxides, total heat lands in a physically plausible band
  (350–520 kJ/kg). Gate the *band*, not a point value — this is a sanity check on units,
  explicitly **not** a calibration.
- With both slag and ash dosed, Σ CH consumed ≤ CH produced, with equality only when the
  pool is exhausted. This is the defect-2 regression gate.
- Every field returned by the layer carries its unit in its name; no function mixes wt%
  with kg/m³.
- `analyze_mix(mix, cement_type="LC3")` does not return OPC phase values, and
  `bogue_calculation` raises on a `bogue_valid: false` record.
- **Frozen-surface gate:** `tests/test_chemistry.py` and `tests/test_clinker_source.py`
  pass **without modification**. If either needs an edit, the change has escaped scope.
- The notebook runs top to bottom and prints the new unit-suffixed fields.

### Traps

- The clamps in `bogue_calculation` are applied *after* C2S is computed from the raw C3S.
  That ordering is correct; preserve it.
- `analyze_mix` computes w/c as water/**cement**. Once slag is handled properly, consider
  whether the hydration model wants w/binder — but changing it alters α and every
  downstream number, so if you change it, say so explicitly rather than folding it in.
- Do not "fix" the 92.7% phase sum. Clinker is not 100% the four major phases; the
  remainder is minor oxides, and forcing normalisation would be wrong.

## WP-2 — Exotic volume accounting

### Current state

`mix_volume` sums over `DENSITIES`, which covers only the seven core materials. **No
exotic in the registry carries a density.** Measured: 150 kg/m³ of calcined clay displaces
~0.058 m³, which *exceeds the entire* `VOLUME_TOLERANCE` of 0.05. Both the batchability
check and `repair_volume` are therefore blind to any exotic dosing, so the "fills 1 m³"
guarantee quietly stops meaning what it says once the exotics panel is used.

### Design

**1. Add `density_kg_m3` to all twelve exotic records** in `data/materials.json`. Use
these values so the implementer does not guess (standard material data, same provenance
convention as the existing core densities):

| Material | kg/m³ | | Material | kg/m³ |
|---|---|---|---|---|
| silica_fume | 2200 | | basalt_fiber | 2650 |
| metakaolin | 2500 | | nano_silica | 2200 |
| rice_husk_ash | 2100 | | graphene_oxide | 1800 |
| limestone_filler | 2700 | | calcium_chloride | 2150 |
| calcined_clay | 2600 | | shrink_reducer | 1000 |
| steel_fiber | 7850 | | polypropylene_fiber | 910 |

**2. Extend `validate_material`** to require `density_kg_m3` on `delta_estimate` records,
matching the existing requirement on `trained_feature` records.

**3. Add `exotic_densities_view()`** — a *new* view, parallel to `densities_view()`.
Do **not** widen `densities_view()`: `tests/test_materials.py` pins `EXPECTED_DENSITIES`
to seven entries as an R6.1 bit-identical migration gate, and that pin is load-bearing.

**4. `mix_volume(mix, exotic=None)`** gains an optional second argument adding
`Σ exotic_mass / exotic_density`. Default `None` preserves today's behaviour exactly, so
every existing caller (the generators, via `enforce_volume`) is unaffected.

### Non-goals (deliberate, do not exceed)

Do **not** wire exotic volume into `ui_logic.compute_metrics`, `ui/`, or `repair_volume`'s
scaling strategy. Surfacing it is a product decision with its own UX question (what should
the app *do* when an exotic-laden mix fails the balance?), and it would pull `ui_logic.py`
into Wave A and break the ownership partition. Capability plus tests only.

### Acceptance gates

- A registry record missing `density_kg_m3` on a `delta_estimate` material is rejected by
  `validate_material` with a readable message.
- `mix_volume(base, {"calcined_clay": 150})` exceeds `mix_volume(base)` by ~0.058 m³
  (150/2600), and `mix_volume(base)` is bit-identical to today's value.
- `EXPECTED_DENSITIES` in `tests/test_materials.py` is **unchanged** (seven entries).
- The existing "≥90% of UCI rows within tolerance" test in `tests/test_physical.py` still
  passes — the core path must not move.
- A registry-edit test in the established `set_materials_path` / `finally` style shows a
  changed exotic density flowing into `exotic_densities_view()` with no code change.

## WP-3 — Curing-time heuristic

### Current state

`estimate_curing_time` computes water/**cement** (not water/binder) *and* adds an
`ash_slag_ratio` term, so substituting cement with slag is penalised twice. A
200 cement / 200 slag / 180 water mix reports 17 days off an apparent w/c of 0.9, when its
true w/b is 0.45.

### Design

Compute `wb = water / (cement + slag + ash)` and replace the raw `ash_slag_ratio` with a
**bounded** SCM fraction, `scm = (slag + ash) / binder ∈ [0, 1]`, so the substitution is
charged once for its dilution effect (through w/b) and once for its genuinely slower
reaction rate (through `scm`) — rather than twice for the same substitution through an
unbounded ratio. Keep the `max(1.0, ...)` floor and the "heuristic" labelling; this stays
a heuristic, it just stops contradicting itself.

### Acceptance gates

- The 200/200/180 mix no longer exceeds a 400/0/180 mix by more than the bounded SCM term.
- Monotonic in w/b; result always ≥ 1 day; a zero-binder mix does not divide by zero.
- **Grep first:** search the suite for pinned curing expectations before changing the
  formula (`tests/test_ui_logic.py`, `tests/test_chemistry.py`, and the mix-ticket golden
  rows are the likely sites). This changes displayed numbers; any pinned value must be
  updated deliberately, with the new value justified in the commit message, never
  loosened to make a test pass.

## WP-4 — Clinker-source validation

### Current state

`load_project_config` validates only the top-level run keys against `DEFAULT_RUN_CONFIG`;
the `clinker_source` dict's contents pass through unchecked into `FUEL_EF[fuel]` and
`GRID_EF[elec]`. Confirmed: a project file naming `"hydrogen"` or `"grid_ZA"` produces an
uncaught `KeyError` traceback instead of the clean exit-1 `CliError` every other input
error in this CLI produces.

### Design

Add `validate_clinker_source(src) -> Optional[str]` to `src/cli.py`, mirroring the shape
of `materials.validate_epd_json` (returns `None` when usable, else a human-readable
message), and call it from `load_project_config`, raising `CliError` on failure. Checks:

- the value is a dict;
- `kiln_fuel`, if present, is a key of `FUEL_EF` — the message must **name the valid
  fuels**, since a user cannot guess `alt_waste`;
- `electricity`, if present, is a key of `GRID_EF`, message naming valid grids;
- `capture.rate`, if present, is numeric in [0, 1];
- `capture.energy_kwh_per_tCO2`, if present, is numeric and ≥ 0.

It lives in `cli.py` rather than `materials.py` because this is boundary validation of
CLI-supplied input, and `ui/config.py` cannot produce a bad key (it builds its selectboxes
from `sorted(FUEL_EF.keys())` and `sorted(GRID_EF.keys())`). Keeping it here also keeps
WP-4's ownership disjoint from WP-2's.

### Acceptance gates

- A config naming an unknown fuel or grid exits 1 with a message listing the valid
  options — no traceback.
- `clinker_scope_split` itself is **unchanged** (it is inside WP-1's file and inside the
  frozen carbon surface). Validation happens at the boundary.
- `capture.rate` of 1.5 or `-0.1` is rejected.
- Every existing test in `tests/test_cli.py` passes unmodified.

## Wave B — WP-5 — Transport mass consistency *(after WP-1 and WP-3 merge)*

Transport carbon sums mass over the seven factor keys only
(`src/chemistry_simple.py:45`, `src/chemistry_advanced.py:294`, `src/ui_logic.py:259` —
the same expression, triplicated), so exotic mass ships free. The bias is small (a few
percent) but systematic and always in the same direction.

Deduplicate the three copies into one function and include exotic mass. This must be
atomic across all three call sites or the tier-equality test
(`test_tiers_same_boundary_simple_slightly_higher`) breaks, which is why it cannot run in
Wave A: two of the three files are owned by Wave A packages.

Also resolve the labelling ambiguity while here: `ui/config.py` describes the input as
"Round-trip haul from plant to site" but the factor is applied one-way to the km entered.
Decide which it is and make the help text and the arithmetic agree.

**Gates:** `carbon_breakdown` still sums exactly to `carbon_for_mode`; the tier-boundary
test passes; a mix with exotics dosed now shows a higher transport term than the same mix
without; `age` is still excluded from transport mass in both tiers.

## Accepted risks (documented, deliberately not fixed)

`calculate_mix_cost` and `calculate_embodied_carbon` iterate the *factors/costs* dict
rather than the mix, so a partial dict silently zeroes the omitted materials. This is not
currently exploitable — `load_project_config` merges onto full defaults and the UI holds
full copies — but the signature invites `custom_costs={"cement": 0.2}`, which would make
every other material free. Fixing it means changing the iteration basis in a function on
the hot path of every metric computation, which is disproportionate to a latent risk with
no live trigger. **Add a docstring warning to each; do not change the iteration.** Revisit
if a caller ever passes a user-authored partial dict.

## Implementation notes (sonnet-ready)

**Sequencing.** Launch WP-1 through WP-4 concurrently — they share no files. WP-1 is the
critical path at ~0.5 d; the other three are ~0.15–0.25 d each. Merge each independently
as it goes green. Run WP-5 only after WP-1 and WP-3 are both in.

**Per-package definition of done.** Code and its tests in one commit; `ruff check .`
clean; the full suite green at the 65% coverage floor; commit message states which
findings it closes and any number it deliberately changed.

**The one thing that would make this worse.** Every gate in this spec is a unit,
conservation, or frozen-surface check. None is "the number matches the literature." If a
gate is failing and the tempting fix is to adjust a coefficient until it passes, stop —
that converts an honestly-wrong model into a dishonestly-right-looking one. Change the
gate only by arguing the physics, in the commit message, the way R7.1's RMSE gate was
consciously revised rather than tuned away.

**Do not weaken a gate to make it pass.** If the hydration heat band cannot be met
honestly, report the number and say why rather than widening the band.
