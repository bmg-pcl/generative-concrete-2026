# R8.1 — Workability from data (the multi-property pattern)

**Status:** spec written, not implemented · **Effort:** ~0.5 d core + ~0.3 d integration
**Depends on:** R7.1 (the conformal/quantile architecture this reuses wholesale). Runs
concurrently with R8.2 — file ownership is disjoint.
**Data:** `data/slump_test.data` is **committed** (103 rows, provenance and integrity checks in
`data/slump_test.PROVENANCE.md` — the canonical UCI host is unreachable from this environment,
so the file was mirror-sourced and validated, not trusted).

## Motivation

Workability is currently a **heuristic**: `physical.workability_flag` thresholds w/b and
superplasticizer dosage and returns advisory prose. Meanwhile a real slump corpus sits
unused in `data_fetcher.AVAILABLE_DATASETS`. Replacing the heuristic with a measured model
where data exists — and *labelling the fallback where it doesn't* — is the point.

The deeper value is architectural. This is the **second measured property**, and it is what
proves the pattern every future property (R8.3 carbon intervals, R9's joint posterior) will
follow: *per-property model + conformal interval + its own support gate*. Getting that
abstraction right once is worth more than the slump number itself.

## Current state — and the three things that make this harder than it looks

1. **103 rows.** Two orders of magnitude less data than the strength corpus. Split-conformal
   on 103 rows leaves a calibration fold of ~25–40, so **the intervals will be wide and the
   coverage estimate itself will be noisy**. That is the honest result, not a bug to tune away.
   The spec's gates are built around admitting it.
2. **A different envelope.** The slump corpus's ranges (cement 137–374, water 160–240, SP
   4.4–19) are *not* the strength corpus's. A mix can be comfortably in-support for strength
   and far outside the slump data. **Each property needs its own support gate** — reusing the
   strength gate would silently over-claim.
3. **No `age` column, and rightly so.** Slump is measured on fresh concrete. The slump model's
   inputs are exactly `PARAM_NAMES[:7]` (the seven materials, no age), which maps cleanly onto
   the existing mix vector — drop the last element, do not invent an age feature.

Column mapping (dataset → repo keys), which the loader must apply:

| Dataset column | Repo key |
|---|---|
| `Cement` | `cement` |
| `Slag` | `slag` |
| `Fly ash` | `ash` |
| `Water` | `water` |
| `SP` | `superplasticizer` |
| `Coarse Aggr.` | `coarse_agg` |
| `Fine Aggr.` | `fine_agg` |
| `SLUMP(cm)` | `slump_cm` *(primary target)* |
| `FLOW(cm)` | `flow_cm` *(secondary target)* |
| `Compressive Strength (28-day)(Mpa)` | `strength` *(NOT used — see below)* |

**Do not train on, or blend in, this corpus's strength column.** It is a different 103-row
experiment from a different lab; mixing it into the 1030-row strength model is a data-provenance
change with its own validation burden, entirely out of scope here. Load it, ignore it, and say
so in the loader docstring.

### WP-1 — the property-model abstraction and the slump model

**A. Loader.** `data_fetcher.load_slump_data()` reads the committed
`data/slump_test.data`, applies the column mapping above, and returns a DataFrame with repo
keys. Mirror `load_data`'s shape and caching. Update the `kaggle_slump` entry in
`AVAILABLE_DATASETS` to record that the file is committed and note its provenance file. **Do
not** add a download path that would hit the blocked host at import time.

**B. The reusable abstraction — this is the real deliverable.** `src/properties.py`:

```python
class PropertyModel:
    """One measured property: point estimate, conformal interval, and its OWN support gate.

    UNITS AND ENVELOPE ARE PER-PROPERTY. A mix in-support for one property may be far
    outside another's training envelope -- each instance carries its own gate, and callers
    must ask the property whether it can speak, never assume.
    """
    def fit(self, X, y) -> "PropertyModel": ...
    def predict(self, X): ...
    def predict_interval(self, X): ...      # (lo, median, hi), like StrengthPredictor
    def novelty(self, X): ...
    def in_support(self, X): ...
    def save(self, path); @classmethod load(cls, path)
```

Reuse R7.1's approach rather than reinventing it: a multi-quantile gradient-boosted model with
per-row rearrangement sorting so the median is the point estimate and the outer quantiles are
the interval, plus split-conformal calibration on a held-out fold, plus a kNN-distance novelty
gate calibrated on the training envelope. **Read `src/models.py` and follow its structure**;
where the small-data regime forces a departure (fold sizes, tree count, k), depart deliberately
and document why in the docstring.

**C. The slump model.** `SlumpModel` (or `PropertyModel` configured for slump) trained on the
seven material columns → `slump_cm`, saved to `models/slump_model.json` and **committed**, same
convention as `strength_quantiles.json`. `flow_cm` is a secondary target: expose it if it comes
nearly free from the same code path, and skip it without ceremony if it does not — slump is what
specifications reference.

**D. Honest degradation.** A public function the integrator will call, e.g.
`slump_estimate(mix) -> dict` returning `{"slump_cm", "lo", "hi", "in_support", "basis"}`,
where `basis` is `"model"` or `"heuristic"`. Out-of-support mixes return the heuristic result
with `basis="heuristic"` and a reason — **never a confident model number outside the envelope**.
`physical.workability_flag` is NOT edited or deleted (a sibling package's frozen file this
wave); it stays the labelled fallback.

### Acceptance gates

- **Measured coverage, whatever it is.** Report empirical coverage of the 90% interval on a
  held-out fold. Gate it loosely — `[0.80, 0.98]` — because 103 rows cannot pin it tighter, and
  **state the measured value in the commit message**. Do not tune the model to land mid-band.
- **Interval width is reported, not minimised.** Record median interval width (cm) in the
  commit message. Wide is the honest outcome of a small corpus.
- The slump support gate is genuinely distinct from the strength gate: exhibit at least one mix
  that is in-support for strength and out-of-support for slump, and assert it. (This is the
  finding that justifies per-property gates — if you cannot find one, say so and show what you
  tried.)
- `lo <= point <= hi` for every row of a 1000-point envelope sweep (R7.1's coherence gate).
- Saved model round-trips: `save` → `load` → identical predictions.
- Out-of-support input returns `basis="heuristic"` with a reason, never a bare model number.
- `load_slump_data()` returns 103 rows with repo-key columns and no nulls; the strength column
  is loaded but unused (assert it is not among the model's features).
- No network access at import or test time — the corpus is committed.

### Traps

- **Do not touch `src/models.py`, `src/physical.py`, `src/ui_logic.py`, or `ui/`.** The
  abstraction goes in the new `properties.py`; wiring is Wave B's. `StrengthPredictor` is not
  refactored to inherit from `PropertyModel` in this package — that is a tempting,
  behaviour-risking refactor of the repo's most load-bearing model, and it is explicitly out of
  scope. Note in the docstring that convergence is future work.
- The tiny corpus makes it easy to produce a model that looks excellent on training data.
  Report held-out numbers only.
- xgboost on 103 rows overfits readily; fewer/shallower trees than the strength model is the
  expected departure, documented.

## Implementation outcome (WP-1, measured)

The gates were met without tuning, and the small-corpus effects landed exactly where the spec
predicted — but one of them landed hard enough to change what Wave B should do with the result:

| Quantity | Measured |
|---|---|
| Held-out coverage (90% interval, 21-row fold) | **0.952** (seed sweep across 6 folds: 0.81–1.00) |
| Median interval width | **23.99 cm** — on a corpus slump range of 0–29 cm |
| Per-property gate justified? | **Yes**, exhibited and asserted |

**The interval is nearly uninformative.** A worked in-support mix returns a point estimate of
22.4 cm with an interval of 3.5–27.5 cm — **83% of the entire physical range**. The point
estimate may well be useful; the interval barely constrains anything, and the coverage estimate
swinging 0.81–1.00 across seeds is the same phenomenon: with ~25 calibration rows, the empirical
90% quantile is close to the fold maximum, so both the width and its coverage are dominated by
noise.

The per-property support gate justified itself concretely and for an interesting reason: every
row in the slump corpus used superplasticizer ≥ 4.4 kg/m³, while the strength corpus spans
0–32.2. So an ordinary SP-free mix — unremarkable for strength — sits outside the slump
envelope entirely. That is precisely the over-claim a shared gate would have hidden.

## WP-1b — CV+ was tried and it did not work (a negative result, kept)

The follow-up above was implemented: cross-conformal / Jackknife+ (Barber et al., *Predictive
inference with the jackknife+*, AoS 2021), on the hypothesis that split-conformal's ~25-row
calibration slice was what made the interval uninformative. **The hypothesis was wrong.**
Measured held-out at the repo's `random_state=42`:

| | split | CV+ |
|---|---|---|
| Median interval width | **23.99 cm** | 24.91 cm *(wider)* |
| Width as % of the 0–29 cm range | **83%** | 86% |
| Held-out coverage | **0.952** | 1.000 *(over-covering)* |
| Coverage across an 8-seed sweep | 0.81–1.00 | 0.81–1.00 *(identical)* |
| Fit wall-time | **~0.07 s** | ~0.65 s |
| Saved artifact | **1.2 MB** | 14.0 MB |

Why it failed, diagnosed rather than guessed: the per-fold quantile models already span ~20 cm
of q05–q95 *before any conformal correction*, so width is dominated by genuine model uncertainty
on 103 rows, not by calibration-slice size. And the seed instability comes from the 21-row
**outer** fold used to *measure* coverage (quantized in ~4.8pp steps), which both strategies
share — CV+ changes what happens inside the training fold, not the fold grading it.

**Disposition:** `strategy` stays a first-class, tested parameter so the comparison remains
reproducible rather than anecdotal, but **split-conformal remains the shipped default** — CV+
costs 11× the artifact and 9× the fit time to be marginally worse. `test_split_is_default_
strategy_for_committed_slump_model` pins that decision so a future "upgrade" has to argue with
the measurement rather than the intuition.

**What this rules out, which is the value of running it:** "we just needed a better calibration
method" is no longer a live hypothesis. The 103-row corpus itself is the binding constraint.
More data is the fix; a cleverer interval is not.

**Consequence for Wave B:** present the slump **point estimate** with its width stated plainly.
Do **not** present the interval as a useful bound — under either strategy it spans 83–86% of the
physical range, and a bound that admits almost every possible outcome misleads by implying it
constrains something.

## Sequencing

WP-1 runs **concurrently with R8.2's Wave A** (disjoint files). Its integration is then folded
into **one shared Wave B integrator** covering both specs, because R8.1's slump display and
R8.2's compliance panel both land in `src/ui_logic.py`, `ui/compare.py`, `ui/config.py`, and the
ticket — two agents there would collide. That integrator: slump metric + interval + basis label
in `compute_metrics` and the ticket, the compliance panel and cross-jurisdiction table, the CLI
flags, and the optimizer compliance constraint.

Same standing rules: code + tests in one commit, targeted foreground tests only, baseline from
the orchestrator, no push, and **no gate weakened to make it pass** — a wide interval or a
mediocre coverage number is a finding to report, not a defect to hide.
