# R8.5 — Optimizers meet the R8 capabilities

**Status:** spec written, not implemented · **Effort:** ~1 d serial; limited parallelism (see §Sequencing — every phase converges on the same three optimizer files, so this spec is deliberately mostly serial. The parallelism lesson cuts both ways.)
**Depends on:** R8.0 (carbon interval, per-material transport, thermal), R8.1 (slump PropertyModel + its support gate), R8.2 (compliance engine + WP-3b's optimizer constraint machinery).
**Scope:** GA, ACO (via `PopulationInverseDesigner`), NSGA-II/III, and — per CLAUDE.md's standing instruction — anything later slotted behind `base_optimizer` (annealing). Everything here enters through the shared objective/constraint helpers, never per-backend forks.

## The two principles that decide every call below

**1. You optimize what the ticket reports.** The optimizer's objective and `compute_metrics`
must be the *same* function of the same config. Any divergence means the optimizer chases a
number the user never sees — and the audit for this spec found exactly one such divergence
already live (§P1). `ui_logic`'s module docstring promises "ONE carbon path, ONE metrics
path, ONE fitness path"; this spec re-earns that promise under the R8 config surface.

**2. The optimizer is the adversary of every model gap.** Optimization pressure finds and
exploits whatever a model gets wrong — that is its job. So a capability enters the objective
or constraint set **only where the underlying number can bear that pressure** (a support
gate, a conservative bound, an exactly-computed quantity), and enters as a **post-hoc
advisory** everywhere else. R1's robust mode is the template; the uncalibrated thermal layer
is the anti-template.

## P1 — Coherence repair: thread `transport_detail` into the optimizer objective *(defect, fix first)*

**Found in the audit for this spec.** `carbon_for_mode` accepts `transport_detail`
(R8.0 WP-E Decision 2), and `compute_metrics` passes it — but `ui/config.py` builds
`ctx.carbon_kwargs` (`ui/config.py:161`) without it, and that dict is what
`recommend_recipe`, `scalarized_fitness`, and `run_nsga` consume. Consequence: with the
per-material transport toggle ON, the displayed/ticket carbon uses registry per-material
transport while **the optimizer still minimizes the global-km path**. SCM substitution
economics differ between the two (slag hauls 150 km vs cement 200 km in the registry
defaults), so the optimizer is not merely offset — it can *rank candidates differently*
than the ticket would.

**Fix:** put `transport_detail` into `ctx.carbon_kwargs` (it is already a
`carbon_for_mode` kwarg, so every downstream consumer picks it up unmodified), and delete
`compute_metrics`' separate parameter in favour of the shared dict *or* keep both wired —
implementer's choice, but ONE source.

**Gate (the coherence contract, kept forever):** a parametrized test asserting
`scalarized_fitness`'s carbon term `==` `compute_metrics(...)["carbon"]`'s carbon for the
same mix under every config axis: simple/advanced × transport_km ∈ {0, 500} ×
transport_detail ∈ {off, on} × factor overrides × clinker_source. Same for the NSGA
objective column. This test is the durable artifact of P1 — the bug it guards against is
exactly the class that green suites missed twice this session.

## P2 — Robust carbon: optimize the upper bound, symmetric with robust strength

R1's flagship move was optimizing the strength **lower** bound. Its carbon mirror is now
cheap: R8.0/D3's `carbon_interval` is analytic linear propagation over the registry's
per-factor uncertainties — fast enough for the inner loop.

- New optional flag `robust_carbon` (default False, independent of the strength `robust`
  flag). When set: the scalarized carbon term and NSGA's carbon **objective column** become
  `carbon_hi` (the +1.96σ bound). **Dimensionality unchanged** — this swaps a column, it
  does not add one (the WP-3b rule: never grow the front's objective count).
- **The incentive this creates is the feature:** uncertainty-weighted carbon makes the
  optimizer prefer *well-characterized* materials. Fly ash's factor is tiny but ±50%; under
  `robust_carbon` its effective cost rises more than slag's (±30%). And an attached EPD
  that tightens a factor's uncertainty genuinely lowers robust carbon — "attach an EPD,
  your guaranteed number improves" is procurement-grade behaviour falling out of the
  arithmetic.
- **EPD uncertainty honesty rule:** EPD records currently replace a factor's *value* only.
  An EPD without an `uncertainty` field keeps the **registry's** uncertainty (disclosed),
  and the EPD schema gains an optional `uncertainty`. Never default-invent a lower
  uncertainty for "measured" data — measured-but-uncharacterized is not ±0.
- Disclosure: returned recipes and the NSGA result dict gain
  `carbon_basis: "point" | "upper_95"`.

**Gates:** with all uncertainties zero, `robust_carbon` output is bit-identical to point
mode; two constructed mixes with equal point carbon but different composition uncertainty —
robust mode must prefer the better-characterized one; tightening one factor's uncertainty
(EPD-style) lowers that mix's objective monotonically; basis disclosed in every output dict.

## P3 — Workability: a slump target the model can honestly support

Only active when the caller *requests* a slump target — never ambient.

- **The slump support gate is the load-bearing constraint** (principle 2): when a slump
  target is set, candidates must be in-support **for the slump model** (its own gate — the
  R8.1 finding that the slump envelope ≠ strength envelope is exactly why). GA: penalty
  term mirroring `OOS_PENALTY_WEIGHT`; NSGA: one added inequality constraint, mirroring the
  existing in-support constraint.
- **The target itself is a soft penalty on the point estimate** (`|slump_point − target|`,
  modest weight), with the basis disclosed in the result.
- **Robust slump is considered and REJECTED, with numbers:** the 90% interval spans 83% of
  the 0–29 cm physical range (R8.1 WP-1b, confirmed unfixable by CV+). A lower-bound slump
  constraint of even 10 cm would exclude nearly the entire in-support region — vacuous
  conservatism that would mostly optimize interval-width noise. The spec's own honesty
  rule: a number that cannot bear optimization pressure does not enter the objective.
  Revisit only when more slump data exists.
- **Disclose the envelope shift.** Every slump corpus row used superplasticizer
  ≥ 4.4 kg/m³, so a slump-constrained design *will* be SP-dosed — that is the corpus
  speaking, not a preference. The returned recipe carries a note to that effect.
- If no candidate satisfies strength target ∧ slump support jointly, report
  `found: False` honestly (the `design_compliant` pattern) — never return an
  out-of-slump-support design with a confident slump number attached.

**Gates:** slump-target run returns designs in slump-support with the basis `"model"`; a
target reachable only outside slump support reports `found: False`; no-slump-target runs
are bit-identical to today; the SP-dosing disclosure appears when the constraint is active.

## P4 — Compliance UX completion (engine exists; the tabs don't speak it yet)

WP-3b shipped `design_compliant` (GA/ACO) and `run_nsga`'s compliance constraint + verified
`"compliance"` output block. Nothing in the UI invokes them.

- Inverse and Pareto tabs gain a "require compliance with the selected exposure class"
  toggle, active only when the Config tab's pack/class selectors name a real pair (the
  R8.2 WP-3a selectors — never a second selector set).
- **Honest-ceiling messaging is the hard part, not the wiring.** Both shipped real packs
  omit `max_scm_fraction` (unsourceable), an omitted rule is UNKNOWN, and WP-3b counts
  UNKNOWN as violated — deliberately, since minimizing carbon maximizes SCM and the missing
  rule is exactly the SCM cap. Therefore a *strict* constrained run against `en206`/`aci318`
  will report `found: False`, correctly. The UI must present this as what it is ("this
  pack's omitted rules make a verified PASS unreachable — see the pack's notes"), and offer
  WP-3b's existing `unknown_counts_as_violation=False` opt-out as an explicit checkbox
  ("allow UNKNOWN rules") with advisory text. Default strict.
- Ticket/output: constrained runs disclose the mode (strict / allow-unknown) alongside the
  existing advisory row.

**Gates:** strict mode against a real pack pins `found: False` (the honest ceiling,
test-pinned so pack-sourcing progress visibly flips it); allow-unknown mode returns designs
whose evaluable rules all PASS; the toggle absent ⇒ bit-identical behaviour; the mode
appears in the output dict and ticket.

## P5 — Thermal: post-hoc advisory only *(considered as a constraint and rejected)*

`adiabatic_temperature_rise` inherits the hydration layer's UNCALIBRATED status. A ΔT cap
is monotone in `cement_mass × heat_coefficient` where the coefficient is the uncalibrated
part — so as an optimizer constraint it is a cement cap wearing false precision. The
recommended pattern for a user who wants mass-pour safety today is a **direct cement-content
cap** (exact, and trivially expressible as a bounds edit), with ΔT shown as the advisory it
already is.

**Do:** returned recipes and NSGA front members gain `delta_t_adiabatic_C` and any
`mass_pour_flag` string (post-hoc, reusing the WP-E disclosure path). **Don't:** no ΔT
term in any objective or constraint until calorimetry data exists. Revisit tied to the
same trigger as the hydration layer's calibration itself.

## Considered and rejected (recorded so they are not re-litigated)

| Capability | Why it stays out of the optimizer |
|---|---|
| Carbonation-uptake bound | Outside A1–A4; crediting uptake in an objective without service-life modelling is greenwashing-adjacent. Informational line only. |
| Carbon-intensity as a 4th NSGA objective | Every intensity-optimal point already lies on the strength/carbon front (it is a ratio of two existing objectives); adding it changes front dimensionality and invalidates every hypervolume baseline for zero coverage gain. |
| Waste factor in objectives | Constant multiplier; moves no optimum — excluded by design since R8.0 WP-A. |
| Maturity curing as a constraint | Uncalibrated α(t); same reasoning as P5. |
| Powers calibration artifact | Evidence for the R9 hybrid, not a runtime input. |

## Sequencing & packages

Mostly serial, deliberately: P1–P3 and P5 all edit `src/ui_logic.py`, `src/generative_ga.py`,
and `src/nsga.py`, so parallel packages would collide on exactly the files where a merge
mistake is costliest. Structure:

- **WP-1 (engine, ~0.5 d):** P1 → P2 → P3 → P5 in one package, one commit each, in that
  order (P1's coherence test then guards P2/P3 as they land). Owns the three optimizer
  files + `tests/test_ui_logic.py`, `tests/test_generative.py`, `tests/test_nsga.py`,
  `tests/test_properties.py` (slump-constraint tests).
- **WP-2 (UI, ~0.3 d, after WP-1):** P4 plus surfacing P2/P3's flags in the inverse/Pareto
  tabs. Owns `ui/*` + AppTest/session-roundtrip tests. New config keys via
  `CONFIG_DEFAULTS` only, established pattern.
- Standing rules unchanged: baseline from the orchestrator, targeted foreground tests only
  (**first line of every prompt this time** — the effort log's recurring F3 note), no gate
  weakened to pass, deviations reported not papered over.

Every default is bit-identical: a user who touches none of the new flags gets today's
behaviour to the last digit, test-gated per phase.
